# Travel URL Ingest — 첨부 URL 본문 확보 및 반영

## 처리 대상

사용자가 링크를 던지는 상황은 대개 셋 중 하나다.

1. **참고 일정** — "이 사람 일정 참고해서 짜줘"
2. **특정 정보 확인** — "여기 캠핑장 예약 방법 나와 있어"
3. **검증 요청** — "이 글 말이 맞아?"

의도를 먼저 판별한다. 불명확하면 한 번만 묻는다.

---

## 네이버 카페·블로그의 구조적 문제

일반 URL fetch가 실패하는 이유:

| 유형 | 증상 | 원인 |
|---|---|---|
| 네이버 카페 | 빈 페이지 또는 로그인 요구 | 본문이 iframe 내부, 상당수가 회원 전용 |
| 네이버 블로그 | 껍데기만 반환 | 본문이 `blog.naver.com/PostView.naver` iframe |
| 티스토리 일부 | 부분 반환 | 지연 로딩 |

---

## 폴백 사다리

**위에서부터 순서대로 시도하고, 성공하면 멈춘다.**

### 1단계 — WebFetch 직접 시도

```
WebFetch(url, prompt="이 글의 여행 일정, 방문 장소, 실용 팁, 비용 정보를 정리해줘")
```

가장 저렴하다. 티스토리·브런치·워드프레스·공식 사이트는 대개 여기서 끝난다.

### 2단계 — 네이버 블로그 iframe 실주소 변환

`blog.naver.com/{id}/{logNo}` 형태라면 다음 주소가 실제 본문이다.

```
https://blog.naver.com/PostView.naver?blogId={id}&logNo={logNo}
```

`m.blog.naver.com/{id}/{logNo}` (모바일)도 시도한다. 모바일 페이지가 더 단순한 HTML을 반환하는 경우가 있다.

### 3단계 — 모바일 URL 변환

| 원본 | 모바일 |
|---|---|
| `cafe.naver.com/...` | `m.cafe.naver.com/...` |
| `blog.naver.com/...` | `m.blog.naver.com/...` |

### 4단계 — 네이버 검색 MCP 우회

URL을 직접 못 읽어도 **그 글을 검색으로 찾으면 요약(description)은 얻을 수 있다.**

```
① URL에서 제목이나 카페명·게시글 번호 추출
② NaverSearch-search_cafearticle / search_blog 로 검색
③ 결과 중 URL이 일치하는 항목의 title + description 확보
```

전문은 아니지만 주제·핵심 내용은 파악된다. **같은 주제로 접근 가능한 다른 글을 추가로 찾아 정보를 보완한다.**

### 5단계 — 브라우저

`claude-in-chrome` 또는 `mcp__remote-devices__Control_Chrome__*`이 있으면 사용자 로그인 세션으로 접근한다. 회원 전용 카페 글은 이 방법이 유일하다.

```
navigate(url) → get_page_text() / get_page_content()
```

**2회 실패하면 즉시 중단한다.** 스크립트 주입 타임아웃과 봇 차단으로 반복 실패하는 사례가 많다. 같은 동작을 계속 재시도하지 않는다.

### 6단계 — 사용자에게 요청

여기까지 왔으면 솔직하게 알린다.

> 이 링크는 회원 전용이거나 자동 접근이 차단되어 있어 본문을 읽지 못했습니다. 브라우저에서 글을 여신 뒤 본문을 복사해 붙여넣어 주시면 그대로 반영하겠습니다. 스크린샷도 괜찮습니다.

**추측으로 내용을 지어내지 않는다.** 못 읽었으면 못 읽었다고 한다.

## 추출 스키마

본문을 확보하면 다음 형태로 구조화해 `/tmp/{trip_slug}/references/{source_id}.json`에 저장한다.

```json
{
  "source_id": "naver-cafe-12345",
  "url": "https://cafe.naver.com/...",
  "platform": "naver_cafe",
  "title": "옐로스톤 캠핑카 7박 8일 후기",
  "published": "2025-08-20",
  "access_method": "browser",
  "confidence": "full",
  "itinerary": [
    {"day": 1, "route": "보즈먼 → 매디슨", "stops": ["Walmart", "West Entrance"],
     "lodging": "Madison Campground", "notes": "체크인 16시 이후 자리 없음"}
  ],
  "spots_mentioned": [
    {"name": "Grand Prismatic", "tip": "본 주차장 대신 Fairy Falls 트레일헤드에 대형차 주차"}
  ],
  "practical_tips": ["곰 스프레이는 현지 Walmart에서 구매"],
  "costs": [{"item": "RV 7박", "amount": "약 2,000달러", "year": 2025}],
  "warnings": ["니들스 하이웨이 터널은 RV 통과 불가"],
  "quotes": []
}
```

`confidence` 값:
- `full` — 본문 전체 확보
- `partial` — 요약·발췌만 확보 (4단계)
- `none` — 접근 실패

## 반영 규칙

### 1. 참고이지 복제가 아니다

사용자가 "참고만 해"라고 하면 **일정을 그대로 베끼지 않는다.** 방문 장소 목록과 실전 팁만 흡수하고, 동선은 `trip-brief.json`의 조건(차량·인원·숙박)에 맞춰 다시 짠다.

### 2. 원문 표현을 그대로 옮기지 않는다

추출한 내용은 **요약하고 재구성**한다. 저작권 문제이자, 원문의 오류를 그대로 옮기는 것을 막는 장치다.

### 3. 시점 검증

여행 정보는 노후화가 빠르다. 글의 작성 시점을 확인하고, **2년 이상 지난 요금·운영시간·규정은 공식 소스로 재확인**한 뒤 반영한다. 재확인 없이는 "{연도} 기준"을 명시한다.

### 4. 출처 명시

노션 페이지에 다음을 남긴다.

```markdown
> 📎 **참고한 글**
>
> [{제목}]({URL}) ({작성 시점}) — {무엇을 참고했는지}
```

### 5. 상충 처리

첨부 글과 공식 정보가 다르면 **공식 정보를 채택**하고 차이를 기록한다.

```markdown
> ℹ️ 참고 글에는 {A}로 되어 있으나, {공식 출처} 기준 현재는 {B}입니다.
```

## 첨부 파일 처리

URL이 아니라 문서(docx·pdf·xlsx·이미지)를 첨부한 경우도 같은 스키마로 처리한다.

| 형식 | 방법 |
|---|---|
| docx | `docx` 스킬 또는 python-docx |
| pdf | `pdf` 스킬 |
| xlsx | `xlsx` 스킬 |
| 이미지 | Read 도구로 직접 열람 |

지인이 만든 일정표를 받는 경우가 흔하다. 이때도 **"일정은 동일할 필요 없고 장소 목록을 최대한 반영"** 이 기본 해석이다. 사용자가 다르게 말했으면 그것을 따른다.

## 다중 URL

여러 링크를 한 번에 받으면 병렬 처리 후 병합한다.

```
Agent 1: URL 1~3 추출
Agent 2: URL 4~6 추출
        ↓
장소별로 병합 → 2건 이상에서 언급된 팁은 신뢰도 상향
              → 상충하는 정보는 공식 소스로 판정
```

병합 결과를 사용자에게 요약해 보여주고 진행한다.

```markdown
## 📎 참고 자료 {N}건 반영

| 출처 | 확보 | 얻은 것 |
|---|---|---|
| 네이버 카페 A | ✅ 전문 | 일정 8일치 · 캠핑장 예약 팁 3건 |
| 블로그 B | ⚠️ 요약만 | 주차 정보 |
| 카페 C | ❌ 회원 전용 | — |

**공통으로 언급된 주의사항**
- {2건 이상 반복된 항목}
```
